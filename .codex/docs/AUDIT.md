## Architecture and product findings from the 2 October audit

The DOCX was a **static, read-only review** at `25252da`: it did not run the app, inspect live Codex data or user databases, benchmark ingestion, or test migrations. Its cited [rolling-release CI run](https://github.com/tajemniktv/TajsTokens/actions/runs/35530583887) is historical evidence for that SHA, not installed-profile, visual, signing, or live-provider validation. The original dispositions were based on narrow checks at `af9e4a9`; A-01 below reflects the later PR implementation. Other findings are not newly benchmarked or runtime-validated here.

The review also found no confirmed counter-reset, compaction, graph-cycle, quota-account mixing or forecast-leakage defect in its inspected paths. It identified the existing separation of native token events, reported quota, history eligibility, reset alerts, forecasts, TT research and API-equivalent prices as a strength to preserve—not as proof that every installed-runtime or source-lineage case is correct.

### A-01: source time must not silently become collection time — implemented in PR #109

The [rollout parser](../../src/TajsTokens.Infrastructure/Ingestion/CodexRolloutParser.cs) and [SQLite store](../../src/TajsTokens.Infrastructure/Persistence/SqliteCodexObservatoryStore.cs) now retain nullable source event time, first capture time and explicit quality separately. Missing/malformed timestamps preserve token amounts but cannot become dated history, forecasting or evaluation input. Schema 9 marks legacy chronology unverified; verified prefix replay enriches only supported source metadata under existing occurrence IDs. The automated regressions cover timestamp precedence, missing/malformed time, migration and replay without duplicated amounts or restamped capture time. Installed-data and visual acceptance are separate from those checks.

28 October installed evidence: component 9 continued ingesting, with two advancing
checkpoints and no changes to existing native amounts/original times in the observed
interval. The installed worker refused an isolated newer component marker without
altering rows, then recovered on the supported marker while withholding untimed
amounts from forecasts. [Scope and hashes](../../docs/source-notes/STAGE2_EVIDENCE_VALIDATION.md)
close A-01's current installed boundary; compressed-history recovery, superseded
evidence retention and broader presentation remain open in PROJECT.md. This does
not claim the user's entire pre-upgrade history was recovered.

### T-01: define TT before promoting the research scalar — selected and implemented

[TtEvaluator](../../src/TajsTokens.Core/Research/TtEvaluator.cs) labels its aggregate experiment `tt-lab/v4-blocks`; [TtWorkloadBasis](../../src/TajsTokens.Core/Models/TtWorkloadBasis.cs) declares `tt-category-basis/v1`. The fitted category weights depend on compatible quota-cost intervals and a local reference mix. The original audit correctly identified that research as insufficient to define an independent public unit.

The user subsequently selected the [October 28 convention](../../docs/source-notes/PRICE_AND_TT_PROPOSAL_2026-10-28.md#public-tt-convention-and-activation-dec-001t-01-dec-005). The implemented public joint-coordinate basis freezes named weights/basket and handles exact, bounded, partial and unsupported quantities separately. It does not promote the quota-learned research scalar. [PROJECT.md T-01/SCORE/D-01](../../PROJECT.md#current-work) owns activation, original-score preservation and acceptance evidence; resource and broader UI acceptance remain separate.

### D-01: clarify evaluator and basis versions — implemented

The DOCX found current v3 project prose alongside the v4 evaluator. The v3 prose is preserved as [dated archive material](../../docs/archive/PROJECT.md). Current PROJECT.md distinguishes evaluator/block aggregation (`tt-lab/v4-blocks`), research category-basis semantics (`tt-category-basis/v1`) and the selected public joint basis/scoring contracts (`tt-joint-basis/v1`, `tt-joint-scoring/v1`). Archived v3 measurements remain v3 evidence; saved original calculations are not silently restated.

### P-01: profile the per-observation write lane before batching it — measured and implemented

The original source inspection identified a serial per-observation connection/transaction cost as a hypothesis. The subsequent isolated comparison measured 10,000 observations at 21.73 s versus 2.20 s with ordered batches of 128. The existing writer/store now preserve reducer order, duplicate and generation semantics, atomic writes and checkpoint-after-success, with reverse-order/parity/failure-restart checks. [Current evidence](../../docs/source-notes/STAGE1_RESOURCE_VALIDATION.md) qualifies those timings; this closes the scoped write-lane finding, not aggregate CPU/disk/RAM acceptance.

### P-02: distinguish Windows distribution from non-Windows compilation — partially addressed

The [README](../../README.md) already identifies the product as a Windows companion and names its Windows requirements. The [app project](../../src/TajsTokens.App/TajsTokens.App.csproj) still substitutes a library target compiling only `CrossPlatformBuildPlaceholder.cs` outside Windows. Release workflows package Windows x64, not a macOS or Linux client. Keep support/release copy explicit: a passing non-Windows app-project build is not portability evidence. A future platform claim needs a launchable packaged UI and platform-specific validation, not a generic framework rewrite.

## Remaining audit boundaries

These explain the audit's outstanding source/product boundaries. Implementation
sequence and completion checkboxes belong to [PROJECT.md](../../PROJECT.md#current-work).

1. **Retain A-01's acceptance scope.** Installed component support, advancing ingestion and newer-version refusal/recovery passed; broader recovery/presentation gates remain in PROJECT.md. Do not mistake the static finding for a measured frequency in live data.
2. **Preserve selected T-01/D-01 semantics.** The frozen public joint basis is independent of the research evaluator and live quota calibration. Keep original scores and archived v3 results under their original versions; changes require explicit selection/restatement rules in PROJECT.md.
3. **Prove a source before expanding remote history.** Account quota can be read on the PC, but another machine's private Codex thread/token files cannot be inferred from it. Tokscale's [Codex scanner](https://github.com/junhoyeo/tokscale#data-sources) reads local session files, while its [multi-device endpoint](https://github.com/junhoyeo/tokscale/blob/bd62b8c4e07269e5314fac06c6d23262dc714633/packages/frontend/src/app/api/me/stats/route.ts) sums submitted history; the [legacy migration](https://github.com/junhoyeo/tokscale/blob/bd62b8c4e07269e5314fac06c6d23262dc714633/packages/frontend/src/lib/db/migrations/0007_add_submitted_devices.sql) can add a device-list row without another machine. If TajsTokens later uses a publisher, shared local API, or an official Codex remote surface, define host/provider/account/source identity, authenticated transport, source-qualified deduplication, durable offline recovery and no raw transcript sync first. Do not introduce a remote agent or background SSH polling by assumption. The current SSH feature stays optional and manual.
4. **Improve live detail only where native evidence supports it.** The current-turn item-type fix is descriptive, not a live tool-event stream. Before a native hook or richer status is added, establish installed-version payload semantics, sanitize *before* storage, prove overlap with rollout events, and test missing/stale/interrupted states. The inspected legacy `notify` payload is a turn-completion notification, not proof of per-tool event coverage.
5. **Seek a Codex-native context/request contract.** The Claude context API cannot justify numeric Codex component shares. A useful Codex Context Inspector can show currently supported context and tool metadata with unknown components labelled unknown; per-component token costs and per-prompt/subagent quota attribution must wait for validated source relationships.
6. **Retain P-01's measured guarantees.** Ordered native batching is implemented with the scoped benchmark/restart evidence above. Aggregate resource budgets and controlled whole-app scenarios remain PERF-001; future persistence changes must retain atomic/replay guarantees.
7. **Evaluate optional pricing and forecast baselines.** Any dynamic price catalog needs effective dates, exact provider/model/bucket coverage, source/version provenance, and unknown-model behavior. External pace or learned-cost heuristics belong in chronological comparisons against existing baselines, including sparse, stale and reset cases—not directly in production claims.
8. **Account management only with ownership evidence.** If multiple Codex homes/logins become a product feature, make source identity explicit and preserve old observations under their original key. Never repair unknown historical ownership with the current login or combine quota windows across unproven accounts.
9. **Keep P-02's release claim narrow.** Support docs already say Windows; distinguish the non-Windows compilation placeholder from a shipped client whenever describing CI or future platforms.

## Adopted design rules and rejected shortcuts

- Keep the existing native Codex accounting, quota, persistence and forecast owners. An external tool is a reference or test oracle, not a second authoritative collector.
- Preserve source-native meanings: **reported quota**, **locally observed tokens**, **API-equivalent price weight**, and **inferred quota cost** are different quantities. Missing/stale/unsupported data is not zero.
- Keep Codex sources and credentials read-only. Local inspection is distinct from durable retention or export; raw prompt text, tool arguments, command bodies, assistant output and secrets must not enter a new spool or remote hub by convenience.
- Do not copy the audits' weaker identity/retention choices: truncated request IDs, unconditional 35/90-day pruning, cross-account quota merging, inferred Claude→Codex lineage as fact, or in-memory-only remote history.
- Do not copy OpenUsage.ai's audited wildcard-CORS/unauthenticated loopback pattern or credential values in process arguments. TajsTokens' local limits API deliberately uses a narrower access boundary.
- Do not infer waiting-for-input, process liveness, cache-rebuild cause, or calibrated forecast confidence from mere item type, timestamps, or a fitted usage ratio.
